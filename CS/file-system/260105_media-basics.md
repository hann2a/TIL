## 1. 모든 건 결국 바이트 스트림
- 파일은 본질적으로 0과 1의 연속 
- 텍스트는 바이트를 문자 인코딩(UTF-8 등) 규칙으로 해석한 결과
- 이미지와 영상은 바이트를 포맷 규격(JPEG, PNG, MP4) 등으로 해석한 결과

## 2. 포맷은 바이트를 해석하는 약속 
- 헤더는 이 파일, 버전, 크기에 대한 정보 
- 메타데이터는 촬영 정보, 색 공간, 회전 정보 등
- 페이로드는 실제 데이터(픽셀/프레임/오디오 샘플)
- 그래서 프로그램은 파일을 읽을 때 바이트를 읽고 규격대로 쪼개서 의미 있는 값으로 변환한다. 

## 3. 이미지는 픽셀 배열 플러스 색 표현 
- 이미지를 가장 단순화하면 2차원 픽셀 격자이고, 픽셀은 보통 색 채널의 묶음이다. 
- RGB라면 픽셀 하나가 3개의 값 
- 흔한 비트 깊이는 채널당 8비트 
- 따라서 픽셀 하나는 3바이트 
- JPEG/PNG 차이는 결국 픽셀을 저장하는 방식으로, PNG는 무손실이고 JPEG는 손실 압축이다. 

## 4. 영상은 이미지 프레임의 시간 배열과 소리의 집합
- 초당 N장의 이미지 플러스 오디오가 영상이다. 
- 그대로 저장하면 너무 크기 때문에 MP4 같은 컨테이너 안에서 코덱이 압축한다. 
- 컨테이너는 MP4/MKV(영상 + 오디오 + 자막을 담는 상자)
- 코덱: H.264/H.265/AV1 (압축/복원 규칙)
- 핵심 아이디어는 프레임 전체를 매번 저장하지 말고, 변한 부분만 저장하자. 

## 5. 웹에 올리고 내리는 것은 결국 바이트를 HTTP로 주고 받는 것 
- 업로드는 내 컴퓨터의 파일 바이트를 HTTp 요청으로 서버에 전송하는 것 
- 다운로드는 서버가 저장한 파일 바이트를 HTTP 응답으로 보내주는 것
- 브라우저/앱은 응답을 받으면서 파일로 저장하거나 화면에 렌더링한다. 
- 핵심은 네트워크에서 오가는 건 파일이 아니라 바이트 스트림이라는 것. 그리고 이 바이트가 무엇인지는 헤더(Content-Type, Content-Disposition)와 파일 자체 포맷 규격이 결정한다는 것. 

## 6. 확장자는 힌트일 뿐 진짜는 포맷 구조이다. 
- 운영체제/브라우저는 보통 확장자를 보고 워드 파일, 이미지 임을 추측하지만 실제로는 파일 내부 바이트가 해당 포맷 규격을 만족해야 정상 해석된다. 
- `docx`, `xlsx`, `pptx`는 겉보기엔 문서지만, 내부적으로는 ZIP + XML 묶음(컨테이너)인 경우가 많다. 
- 그래서 이름만 바꾼다고 워드가 엑셀이 되지 않는다. 

## 7. 웹에서 보인다 vs. 다운로드 된다는 Content-Type/Disposition 차이 
- Content-Type은 이 바이트는 무슨 종류의 데이터인지 
- Content-Disposition은 브라우저가 화면에 띄울지, 파일로 저장할지 힌트 
    - inline: 가능하면 화면에서 바로 표시 
    - attachment: 다운로드 유도 
- 그래서 같은 파일이라도 서버가 어떤 헤더를 주느냐에 따라 웹에서 재생/표시 되거나 다운로드 된다.

## 떠오른 질문 
### 그럼 옵시디언이 마크다운을 조작할 수 있는 것처럼<br/>워드 같은 인터페이스를 구현해서 <br/>마크다운으로 저장하는 프로그램을 나도 구현할 수 있는지?<br/><br/>그런 앱이 존재하는지?

#### 이미 존재하는 대표 사례
- Typora: 미리보기 창 없이 문서가 곧 렌더링된 형태로 편집하는 스타일의 마크다운 에디터
- MarkText: 오픈소스 마크다운 에디터로, 실시간 렌더링 중심의 UX를 제공
- Milkdown: Typora 같은 WYSIWYG 마크다운 에디터를 만들기 위한 프레임워크/에디터 기반(프로즈미러+Remark 등)

#### 구조화 문서 모델(AST) 방식으로 구현할 수 있다. 
- 내부적으로는 문서를 트리로 유지하고 저장할 때 그 구조를 Markdown으로 직렬화한다. 
- 대표적으로 ProseMirror + prosemirror-markdown이 Markdown <-> 문서모델 파서, 시리얼라이저 제공

#### 포폴용 미리 생각해보기 
- 핵심 문법: heading / paragraph / bold/italic / link / list(중첩) / code block
- 목표: 지원하는 문법은 100% 라운드트립<br/>
    (A) 첨부파일(이미지/파일 드래그앤드롭, 상대경로 관리)<br/>
    (B) diff 기반 저장(변경 최소화, 충돌 방지의 기초)<br/>
    (C) 플러그인 구조(블록 타입 확장 가능)<br/>

### 이미지와 여타 텍스트로 구성된 텍스트 파일은 컨테이너라는 개념이 좌지우지하는건지? 

#### 모양이 결정되는 법 
1. 픽셀로 결정(래스터) 
- 어떤 위치의 픽셀이 어떤 색이냐가 모양을 만든다. 즉, 그림은 픽셀 값의 집합으로 정의된다. 
2. 명령으로 결정(벡터) 
- SVG 같은 벡터는 그리기 명령을 저장한다. 이 명령도 결국 바이트로 저장되므로, 비트만으로 모양이 결정된다.
